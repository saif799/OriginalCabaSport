# Storefront performance baseline — 2026-09-08

First **page-level** measurement of storefront speed and payload: no Lighthouse,
no bundle analyzer, no `web-vitals`, no CI existed before this. Image payload
specifically *had* been measured once, for [ADR-0007](../adr/0007-uploaded-images-are-transformed-at-write-time.md)
(375 rows, 116 images over 300 KB totalling 282 MB, a 12-card grid at ~16 MB) —
that decision's numbers are the only prior art, and they cover uploads, not pages.

This is a **diagnosis, not a fix**. No application code was changed to produce
it. Findings are ranked at the bottom; acting on them is a separate decision.

Units: `KB` means 1024 bytes throughout, matching Lighthouse's reporting.

## Scope, and what it deliberately excludes

Measured: the **storefront** only, locale **`fr`**, two pages.

| | URL |
|---|---|
| Home | `/fr` |
| Product | `/fr/product/a5370eb7009` |

Not measured, all deliberate:

- **`/admin`** — one operator on desktop; client weight there is an annoyance, not a cost.
- **`/products`** (catalog) — so `components/filterTool.tsx` (512 lines, client) is unmeasured. It is the most likely source of catalog weight and remains an open question.
- **Locale `ar`** — RTL and different font shaping may behave differently. See finding 2, which is partly about `ar` and was found anyway.
- **Real network conditions from Algeria.** See "How to read these numbers".
- **Vercel/Neon/R2 billing.** "Cost" here means bytes the customer downloads, not money.

## How to read these numbers

Runs were **local** — `pnpm build` + `pnpm start` on `localhost:3000` — not against
the Vercel deployment. That choice has a sharp consequence:

- **Byte weights are truthful.** Same bundles, same R2 objects, same compression behaviour.
- **Latency is comparable only to itself.** LCP, TTFB and Speed Index reflect this
  machine and this connection under Lighthouse's simulated throttling. They are a
  baseline to re-run identically, **not** an estimate of what a customer in Algeria sees.
  A customer's real numbers will be worse.

Method: `npx lighthouse` 13.4.1, default **mobile** profile (1.6 Mbps, 150 ms RTT,
4× CPU slowdown), headless Chrome, **3 runs per page, median reported**. Byte
weights come from the median run's `network-requests` audit, which is the only
per-route attribution available here — the Turbopack build emits no size table,
no route→chunk manifest, and no source maps.

Compression note: local `next start` serves **gzip**; Vercel serves **brotli**.
Transfer figures below are therefore slightly **pessimistic** against production.

## Server-side time

Timed by calling the real query functions directly against the production Neon
database (`eu-central-1`, Frankfurt). 10 warm iterations, median.

| Query | Round-trips | Warm median |
|---|---|---|
| `getVisibleCollections()` | **4** | 323 ms |
| `getStorefrontProductDetail()` | **2** | 155 ms |

That is **≈81 ms per round-trip** (323 ÷ 4). Note this figure is *total* time per
round-trip — network latency and query execution together. Nothing here isolates
one from the other, so "the database is slow" and "Frankfurt is far" are both
still live explanations.

### The round-trip chain

```
getVisibleCollections()
  1. select storefrontCollections            (visible, ordered)
  2. select storefrontCollectionItems         needs #1's collection ids
  3. products baseSelect                      needs #2's shoeIds
  4. attachPrimaryImages                      needs only shoeIds — see below
```

Steps 1→2→3 are **strictly sequential**: each needs the previous query's result.

Step 4 is **not**. `attachPrimaryImages` calls
`fetchImagesByShoeId([...grouped.keys()])`, and those keys are a *subset* of the
shoeIds already known at step 2 — it depends on step 3 only because it is written
to run after it. The same is true of `getStorefrontProductDetail`'s two
round-trips: the second is keyed by the `shoeId` argument, not by the first
query's result, so **both** are parallelisable as written.

This is **not** an N+1 — the reads are properly batched by id. It is a **latency
chain**, and part of it is a chain only by construction.

Both measured pages are `export const dynamic = "force-dynamic"`, so this cost
is paid **in full on every single request**. Unthrottled `curl` TTFB was 369 ms
(home) and 307 ms (product) against warm medians of 323 ms and 155 ms — i.e. the
database chain is essentially all of home's TTFB.

### Cold start

Three samples of the **first call in a fresh Node process**, versus warm:

| Sample | First call | Next call, same process |
|---|---|---|
| After ~7 min idle, machine quiet | 1825 ms | 308 ms |
| Immediately before the warm benchmark | 2370 ms | — |
| Concurrent with the test suite (machine under load) | 3196 ms | 1100 ms |

The first row is the trustworthy one: its 308 ms follow-up matches the 323 ms
warm median, confirming the machine was not loaded. The third row is
contaminated and is listed only to show the spread.

**This does not isolate Neon compute wake.** The first call conflates process
start, TLS handshake, and any Neon resume. All that is established is that a
first call costs **1.8–3.2 s** against a ~310–320 ms warm median. Attributing
that to Neon specifically would need a separate experiment.

`getStorefrontProductDetail` has no cold figure because it ran *after*
`getVisibleCollections` in the same process, on an already-established
connection — there was no cold state left to measure.

**Important caveat:** all three of this product's images are legacy `.avif`
objects with **no Renditions**. So the pinned page is typical — legacy *is* the
common case today — but **this baseline does not measure the ADR-0007 Renditions
path.** A product uploaded after ADR-0007 has not been measured.

Legacy share, re-derivable:

```sql
select count(*) as total,
       count(*) filter (where cloudflare_image_id not like '%\_800.webp') as legacy
from shoe_images;
-- 2026-09-08: total 376, legacy 260 (69%)
```

Note `CLAUDE.md` says "~327 rows" have no renditions. That number and this one
disagree; `lib/scripts/backfillImageRenditions.ts` exists and converting rows
would move it downward, so 260 is the live figure and the 327 is probably stale.
Not chased here.

## Findings, ranked

**1. The homepage pays 4 round-trips (~323 ms) on every request, and one of them
need not be in the chain.**
`force-dynamic` means nothing is cached. Steps 1→2→3 are genuinely sequential,
but `attachPrimaryImages` (step 4) already has the shoeIds it needs at step 2, so
it could overlap step 3 — as could both of `getStorefrontProductDetail`'s two
round-trips. Levers, cheapest first: **`Promise.all` the independent reads**
(~81 ms off home, ~78 ms off product, no schema change); then collapse 1→2→3
into a join/CTE; then cache the grid.

**2. 93 KB of fonts on every page — including Arabic glyphs on the French page.**
Three families are declared in `app/layout.tsx`: `DM_Mono`, `Cairo`, `Anton`.
`Cairo` declares `subsets: ["arabic", "latin"]`, and its files load on `/fr`.
Fonts are 19% of home transfer weight and more than HTML and CSS combined. The
existing code comment justifies why Cairo is a variable on `<html>` (Radix
portals mount outside the storefront subtree) — that reasoning is about CSS
scoping and does not require shipping Arabic glyph files to French visitors.

**3. LCP is ~3.8–4.0 s on both pages, well over the 2500 ms threshold.**
The worst metric on the board; the gap from FCP (1224 ms) to LCP is ~2.6 s.
Lighthouse's `largest-contentful-paint-element` audit returned nothing on either
page, so **the LCP element was not identified** — the hero and the first carousel
image are suspects, not conclusions. Identifying it is the first step, not
optimising a guess. Note the local-run caveat: a real customer's LCP is worse.

**4. The hero is 84.4 KB and is the largest single asset on the homepage.**
`public/hero/hero-mobile-828.webp` (86,188 B on disk) — a static file, outside
both the Renditions pipeline and the custom image loader. `components/storefront/Hero.tsx`
uses `<picture>`, so the size served is bounded by viewport: desktop
(`min-width: 768px`) gets 44,416–238,942 B, mobile 50,058–239,756 B. A 1280-wide
laptop actually gets **44,416 B — half the mobile hero**. The 239,756 B mobile
1200w file goes to high-DPR *phones*, which is the worst realistic case and the
one worth checking against finding 3.

**5. The shared app-shell chunk carries ~25 KB of unused JS.**
`chunks/0e689ab2da27be34.js`: 66.1 KB transfer, 212 KB raw, ~38% unused on home.
It loads on both pages. Module-level attribution was not possible — the build
emits no source maps — so *what* is unused is not yet known.

**6. Product page TBT is 320 ms, over the 200 ms threshold and 3× home's.**
The product page ships 227.7 KB of JS across 19 requests versus home's 192.1 KB
across 15. `components/storefront/OrderForm.tsx` is 518 lines and client-side.
Not confirmed as the cause — see finding 5 on the missing attribution.

**7. A first request after idle costs 1.8–3.2 s of server time.**
See the cold-start table above. Lighthouse never sees this — it warms the
connection on its first run. A customer arriving after a quiet period pays
something in this range on top of everything else, and `force-dynamic` means
there is no cached page to serve them meanwhile. The cause is not isolated.

## Reproducing this

```bash
pnpm build && pnpm start
npx lighthouse http://localhost:3000/fr \
  --only-categories=performance --output=json \
  --output-path=./lh-home.json --chrome-flags="--headless=new"
```

Three runs per page, take the median. Query timings came from a throwaway `tsx`
script (not committed, per the agreed scope) that called `getVisibleCollections`
and `getStorefrontProductDetail`. It passed a second `neon-http` client as
`exec` so that `getStorefrontProductDetail` took its uncached path — without
that, React `cache()` would have made every warm iteration a no-op.
`getVisibleCollections` has no `cache()` wrapper and needed no such handling.
Round-trips were counted by wrapping `globalThis.fetch`, which the neon-http
driver uses for every query.

## Open questions this baseline does not answer

- What `/products` and `filterTool.tsx` cost.
- Which element is actually LCP on either page.
- Whether `ar`/RTL renders more slowly than `fr`.
- What a Renditions-bearing product page weighs versus this legacy one.
- What any of this looks like on a real connection from Algeria.
- Which modules make up the unused 25 KB in the shared chunk.
- How much of the 1.8–3.2 s first-call cost is Neon compute wake versus TLS.
